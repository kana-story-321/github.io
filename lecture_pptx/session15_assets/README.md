## 「引受判定マスタ表」の列設計 (10列)

| 列 | 名前 | 説明 | 記入例 |
|---|---|---|---|
| A | 条件ID | `RULE-001` などの一意ID(削除より "無効化" 推奨) | RULE-004 |
| B | カテゴリ | 年齢 / 健康 / 職業 / 既往歴 / 金額 / その他 | 健康 |
| C | 対象商品 | 医療 / がん / 死亡 / 学資 / 介護 / 全て | 医療 |
| D | 条件詳細 | AI が読む条件本文(自然言語で具体的に) | 高血圧治療中で 収縮期160mmHg以上 |
| E | 判定 | YES / YES(条件付) / 要確認 / NO | 要確認 |
| F | 判定理由 | なぜこの判定になるか、1〜2文で | 血圧コントロール状態により条件付き引受の可能性 |
| G | 追加確認 or 代替案 | 要確認→確認項目 / NG→代替案商品 | 追加確認: 診断書+直近3ヶ月血圧記録 |
| H | エスカレ先 | 要確認時の引き上げ先(部署/担当) | 引受査定課 Aチーム |
| I | 根拠 | 内規条項 / パンフページ / メール引用 / "口伝" | 医療保険引受基準書 v2019 §3.2 |
| J | 最終更新 | 日付 + 更新者名 | 2026-07-14 田中 |

### なぜこの10列か

- **A(条件ID)** があるから、AI 判定結果に「参照した条件」を紐付けられる → 後で監査できる
- **I(根拠)** があるから、「なぜこのルール?」に答えられる → "口伝" もそのまま書き残す(要正式化の目印になる)
- **J(最終更新)** があるから、いつ誰が変えたか追える → 属人化を防ぐ
- **G(追加確認/代替案)** で 要確認/NG のあとの動きまで書く → 現場で "次何する?" に困らない

## 動作確認 (20分)

### A. マスタ表への統合(演習1 の確認)

1. デモナレッジ01(口伝メモ)から「妊娠12週未満は要確認」を抽出 → マスタ表に1行入る
2. デモナレッジ02(Slack)の 2024/09/08 発言でも同じ内容 → 1行に統合、根拠列に両方書く
3. 記入例シートの `RULE-014` と一致していることを確認

### B. AI 一次判定(演習2 の確認)

1. マスタ表を CSV でコピー
2. Gemini に貼り付け:
   ```
   以下はうちの保険引受判定マスタ表(CSV)です。
   [CSV貼付]
   
   これをルールとして、次の顧客について一次判定してください。
   顧客: 45歳男性 / 高血圧治療中(1年経過、コントロール良好) / 医療保険希望
   
   出力形式:
   - 参照した条件ID: RULE-XXX
   - 判定: YES/NO/要確認
   - 理由: 1〜2文
   - 次のアクション: 顧客への説明/確認項目/エスカレ先
   該当ルールがない場合は "該当なし → 要確認 (人が判定)" と返してください。
   最終判断は引受査定課が行います。
   ```
3. Gemini の出力に「参照した条件ID: RULE-005」が入っていることを確認

### C. 該当なしフォールバックの確認

- マスタにない条件を渡す:
  「顧客: 30歳男性 / パラグライダー競技選手 / 死亡保険」
- Gemini が「該当なし → 要確認 (人が判定)」と返すことを確認

## トラブルシューティング

| 症状 | 対処 |
|---|---|
| ナレッジから条件が抽出できない | Gemini に「以下から引受判定条件を抽出して」と依頼、素材ごと丸投げでOK |
| マスタ表の重複行が減らない | カテゴリ(B列)でソート → 同じカテゴリで同じ条件詳細が並んでたら統合 |
| Gemini が「該当なし = YES」で返す | プロンプトに「該当なし = 要確認」を明示的に書く |
| Gemini が条件ID を出力しない | プロンプトの出力形式に「- 参照した条件ID: RULE-XXX」を必ず含める |
| マスタ表が長すぎて Gemini に貼れない | カテゴリ別に分割、または CSV ファイルとして添付 |

## 継続運用のコツ

- **月1回15分の見直し会議**: 更新ログを見返し、追加・修正・無効化を1件でも進める
- **"口伝" の正式化**: 根拠列に "口伝" と書かれた行を、月1件でも正式ルール化していく

- **削除より無効化**: マスタ表に "有効/無効" 列を追加、無効行は行末に移動して残す
